# ADR-003 - Validación Ed25519 + HMAC-SHA256 para Licencias

**Estado:** Aprobado  
**Fecha:** 2026-10-19  
**Autor:** Lead Architect  
**Norma:** ISO/IEC 27001, ISO/IEC 42001, ISO/IEC 17025

## Contexto

El sistema legacy BALANSOFT-WS utilizaba exclusivamente JWT con HMAC-SHA256 para autenticación y validación de sesiones. Este enfoque tenía las siguientes limitaciones:

1. **Falsos positivos en validación**: Cualquier token válido firmado con el secreto compartido era aceptado, sin verificar la procedencia de la licencia.
2. **Sin atestiguamiento asimétrico**: No había forma de verificar que una licencia provenía del License Manager oficial.
3. **Key management débil**: El secreto HMAC-SHA256 era único para todo el sistema, sin separación por cuenta o licencia.

## Decision

Añadir firma digital Ed25519 (curva elíptica de curva 25519) para la validación de licencias, manteniendo HMAC-SHA256 para JWT de sesión:

### Flujo de Validación de Licencia

1. **Registro/Alta de cuenta**: `POST /api/v1/auth.register` crea la empresa y usuario Admin
2. **Validación contra License Manager**: `POST /api/v1/panel/verificar-licencia` valida la clave contra el LM (local `127.0.0.1:9001/api/v1` o central `https://lm.balansoft.com.ve/api/v1`)
3. **Si la licencia es válida y activa**: `POST /api/v1/auth.register` completa el registro y vincula la licencia
4. **Vinculación hardware**: La licencia se vincula al `hardware_id` del equipo titular (único por licencia)
5. **Cada login**: El backend valida la licencia Ed25519 contra LM y emite JWT con datos de cuenta

### Flujo de Validación JWT (sesión)

1. **Login**: `POST /api/v1/auth.login` con email + password (BCrypt) + validación licencia Ed25519
2. **JWT emitido**: Contiene `sub` (usuario), `id_empresa`, `rol`, `exp`, y marca `offline: true/false`
3. **Refresh token**: `POST /api/v1/auth.refresh-token` renueva el access token
4. **Validación por recurso**: Cada endpoint verifica el JWT y extrae `id_empresa` para filtrado

## Consecuencias

### Consecuencias Positivas

1. **Seguridad criptográfica fuerte**: Firmas asimétricas Ed25519 imposibles de falsificar sin la clave privada
2. **Licencias un solo uso**: `BS-XXXX-XXXX-XXXX` (SHA-256, 7 días máx.) impiden compartir licencias entre estaciones
3. **Validación contra LM**: La clave debe ser validada contra el License Manager, evitando licinas generadas localmente
4. **Key management separador**: Clave pública del LM verificada en cada estación; clave privada guardada seguramente en el LM
5. **Compatibilidad retroactiva**: HMAC-SHA256 se mantiene para JWT de sesión; solo la validación de licencia cambia

### Consecuencias Negativas

1. **Complejidad de key management**: Necesidad de distribuir y gestionar claves públicas en cada estación
2. **Latencia en validación**: Cada login requiere validación contra LM (optimizable con caché de 24h)
3. **Dependencia de LM**: Si el License Manager está caído, el alta de nuevas cuentas queda bloqueada (aunque licencias DEMO/MONOPUESTA pueden tener fallback)
4. **Necesidad de `lms_stub.py`**: Para desarrollo sin conexión al LM central

### Mitigaciones

- **Caché de validación**: `lms_stub.py` para desarrollo; validaciones exitosas cached por 24h en producción
- **Licencias DEMO**: Tienen grace period de 7 días (`OFFLINE_GRACE_DAYS=7`) sin necesidad de validación online constante
- **MONOPUESTA**: Pueden operar en modo local sin validación central constante
- **Central timeout**: Default 30s con 1 reintento único ante timeout (log: «intento n/2»)
- **Superficie expuesta**: `/api/v1/health` y `/api/v1/environment` exponen el motor BD pero no credenciales (`sanear_password_en_mensaje` MED-001)
